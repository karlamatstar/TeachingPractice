# ai_quality_final_project 상세 정리

---

## 1. 프로젝트 한 줄 목적

> **AI 교육과정 안내 챗봇의 답변 품질을 자동으로 테스트·평가·보고하는 QA 자동화 파이프라인**

"챗봇이 잘 답하는가"를 사람이 일일이 확인하는 것이 아니라,  
**데이터 기반으로 자동 측정하고 보고서까지 자동 생성**하는 것이 핵심이다.

---

## 2. 전체 흐름 (파이프라인)

```
[테스트케이스 파일]
  data/test_cases.json
        │
        ▼
[교육과정 안내 챗봇]  ← knowledge_base.py (기준 정보 참조)
  service_agent.py
        │
        ▼
[규칙 기반 1차 검증]
  rule_validator.py
  → 예상 키워드 포함 여부만 확인 (빠르고 단순한 필터)
        │
        ▼
[AI 평가자]           ← knowledge_base.py (채점 기준 참조)
  judge_agent.py
  → 정확성 / 근거성 / 유용성 / 안전성 각 5점 채점
        │
        ▼
[점수 집계 / 판정]
  → PASS / REVIEW / FAIL 결정
        │
        ▼
[리포트 자동 생성]
  report_generator.py
  → JSON, CSV, Markdown 3종 출력
        │
        ▼
[Streamlit 대시보드]
  dashboard/streamlit_app.py
  → 결과 시각화
```

## 3. 각 파일의 역할과 "왜 이게 필요한가"

### 3-1. config.py — 환경설정

| 항목 | 내용 |
|------|------|
| 역할 | 프로젝트 경로, API Key, 결과 저장 폴더 관리 |
| 왜 필요한가 | 경로나 키 값이 코드 여기저기 흩어지면 수정할 때 하나씩 찾아야 함. config.py 하나만 고치면 전체 반영되도록 중앙화 |
| 이게 없으면 | 다른 모든 파일이 경로를 직접 하드코딩해야 해서 유지보수 불가 |

---

### 3-2. knowledge_base.py — 기준 정보

| 항목 | 내용 |
|------|------|
| 역할 | 교육과정의 공식 정보(시간, 출결 규정, 수료 기준 등)를 문자열/딕셔너리로 보관 |
| 왜 필요한가 | Service Agent는 "무엇을 답해야 하는가"의 기준이 필요하고, Judge Agent는 "정답이 무엇인가"의 기준이 필요함. 두 Agent 모두 이 파일을 참조 |
| 이게 없으면 | 챗봇이 뭘 기준으로 답할지 모르고, 평가자도 뭘 기준으로 채점할지 모름 |

포함해야 할 정보 예시:
- 총 교육시간: 320시간
- 지각 3회 = 결석 1일
- 수료 기준: 전체 훈련시간의 80% 이상 출석
- 취업지원: 이력서 첨삭, 모의면접, 취업 상담
- 교육과정 범위 외 질문은 모른다고 안내

---

### 3-3. data/test_cases.json — 테스트케이스

| 항목 | 내용 |
|------|------|
| 역할 | 챗봇에게 던질 질문 목록과 기대 결과를 정의 |
| 왜 필요한가 | 테스트 대상이 명확해야 자동화가 가능. 질문·기대 키워드·정책이 미리 정의되어 있어야 파이프라인이 반복 실행 가능 |
| 이게 없으면 | 매번 사람이 직접 질문을 입력해야 하고, 자동화 의미가 없어짐 |

7개 테스트케이스 구성:

| case_id | 유형 | 목적 |
|---------|------|------|
| TC-001 | Happy | 교육시간 정확히 아는가 |
| TC-002 | Happy | 출결 규정 정확히 아는가 |
| TC-003 | Happy | 수료 기준 정확히 아는가 |
| TC-004 | Happy | 취업지원 안내 가능한가 |
| TC-005 | Edge | 범위 외 질문에 모른다고 하는가 |
| TC-006 | Negative | 위험 요청을 거절하는가 |
| TC-007 | Edge | 복합 질문에 모두 답하는가 |

---

### 3-4. service_agent.py — 챗봇 (Service Agent)

| 항목 | 내용 |
|------|------|
| 역할 | 실제 교육과정 안내 챗봇. 테스트케이스의 질문을 받아 답변 생성 |
| 왜 필요한가 | 평가할 대상 답변이 있어야 평가가 가능. 평가 파이프라인의 입력을 만드는 핵심 |
| 이게 없으면 | Judge Agent가 채점할 답변 자체가 없음 |
| 구현 방식 | API 없이도 동작하도록 규칙 기반(if/elif) 모의 챗봇으로 구현 |

동작 방식:
1. knowledge_base.py에서 기준 정보 불러오기
2. 질문 키워드 매칭으로 해당 정보 반환
3. 매칭 안 되면 "확인할 수 없습니다" 반환
4. 위험 키워드 감지 시 "도와드릴 수 없습니다" 반환

---

### 3-5. rule_validator.py — 규칙 기반 1차 검증

| 항목 | 내용 |
|------|------|
| 역할 | AI 평가 전에 단순 규칙으로 먼저 걸러내는 필터 |
| 왜 필요한가 | AI 평가는 비용이 들고 느림. 명백한 오류(키워드 아예 없음)는 AI 없이도 잡을 수 있음. AI 평가가 이상하게 나와도 최소한의 기준은 보장 |
| 이게 없으면 | 모든 답변을 AI가 처리해야 해서 비효율적이고, AI 오평가에 대한 보조 수단이 없음 |

검증 방식:
- `expected_keyword`가 챗봇 답변에 포함되어 있는가
- 포함 → `PASS`, 미포함 → `FAIL`
- 결과: `{ keyword_found: true/false, rule_status: "PASS"/"FAIL", rule_reason: "..." }`

---

### 3-6. judge_agent.py — AI 평가자 (Judge Agent)

| 항목 | 내용 |
|------|------|
| 역할 | AI(LLM)가 챗봇 답변을 4가지 기준으로 채점 |
| 왜 필요한가 | 규칙 검증은 키워드 유무만 봄. 실제로 "잘 설명했는가", "근거가 있는가", "도움이 되는가"는 LLM만이 판단 가능 |
| 이게 없으면 | 키워드 포함 여부만으로 품질 판단 → 형식은 맞지만 엉뚱한 답변도 PASS가 됨 |

평가 항목:

| 항목 | 의미 | 배점 |
|------|------|------|
| accuracy | 기준 정보와 일치하는가 | 1~5점 |
| groundedness | 근거 있는 답변인가 (hallucination 없는가) | 1~5점 |
| helpfulness | 사용자에게 실질적으로 유용한가 | 1~5점 |
| safety | 위험하거나 과장된 표현이 없는가 | 1~5점 |

출력 형식: JSON (Structured Output 방식)
```json
{
  "accuracy": { "score": 5, "reason": "..." },
  "groundedness": { "score": 5, "reason": "..." },
  "helpfulness": { "score": 5, "reason": "..." },
  "safety": { "score": 5, "reason": "..." },
  "overall_decision": "PASS",
  "summary": "..."
}
```

---

### 3-7. report_generator.py — 리포트 생성

| 항목 | 내용 |
|------|------|
| 역할 | 평가 결과를 JSON, CSV, Markdown 3가지 형식으로 자동 저장 |
| 왜 필요한가 | 결과가 터미널에만 출력되면 공유·기록·분석이 불가능. 파일로 남겨야 이력 관리와 보고가 가능 |
| 이게 없으면 | 실행할 때마다 결과가 사라지고 팀 공유나 문서화가 안 됨 |

출력 파일:
- `evaluation_result.json` — 전체 상세 결과 (개발자용)
- `evaluation_result.csv` — 항목별 점수 요약 (엑셀로 열기 가능)
- `final_quality_report.md` — 사람이 읽는 최종 보고서

---

### 3-8. main.py — 파이프라인 실행

| 항목 | 내용 |
|------|------|
| 역할 | 모든 모듈을 순서대로 호출하여 파이프라인 전체를 실행 |
| 왜 필요한가 | 각 모듈이 독립적으로 잘 만들어져 있어도 실행 순서와 데이터 흐름을 연결하는 진입점이 필요 |
| 이게 없으면 | 파일을 하나씩 직접 실행해야 하고 자동화가 안 됨 |

실행 순서:
1. test_cases.json 불러오기
2. 각 테스트케이스 순회
3. service_agent → 답변 생성
4. rule_validator → 1차 검증
5. judge_agent → AI 채점
6. 결과 수집
7. report_generator → 3종 파일 저장
8. 완료 메시지 출력

---

### 3-9. dashboard/streamlit_app.py — 대시보드

| 항목 | 내용 |
|------|------|
| 역할 | 저장된 JSON/CSV 결과를 브라우저에서 시각화 |
| 왜 필요한가 | 숫자 파일만으로는 전체 품질 상태를 한눈에 파악하기 어려움. 차트·표로 보여야 빠르게 문제 케이스를 식별 가능 |
| 이게 없으면 | JSON/CSV를 직접 열어 수동으로 해석해야 함 |

## 4. 작업 순서 — 왜 이 순서여야 하는가

```
1단계: config.py
   → 경로와 설정이 없으면 다른 어떤 파일도 저장 위치를 모름

2단계: knowledge_base.py
   → 챗봇과 평가자 모두 이 기준 정보에 의존함

3단계: data/test_cases.json
   → 테스트 대상이 없으면 실행할 게 없음

4단계: service_agent.py
   → 평가할 답변을 먼저 만들어야 평가 가능

5단계: rule_validator.py
   → 답변이 생성된 후 1차 필터 적용

6단계: judge_agent.py
   → rule_validator 결과와 함께 AI 채점

7단계: report_generator.py
   → 모든 평가가 끝난 후 결과를 파일로 저장

8단계: main.py
   → 전체를 연결하는 진입점 (모든 모듈 완성 후 작성)

9단계: dashboard/streamlit_app.py
   → 결과 파일이 존재해야 시각화 가능 (마지막 단계)
```

## 5. 의존 관계 요약

```
config.py
    └── 모든 파일이 의존

knowledge_base.py
    ├── service_agent.py 가 참조
    └── judge_agent.py 가 참조

data/test_cases.json
    └── main.py 가 읽음

service_agent.py
    └── judge_agent.py 입력 생성

rule_validator.py + judge_agent.py
    └── report_generator.py 가 결과를 받아 저장

report_generator.py
    └── streamlit_app.py 가 저장된 파일을 읽음

main.py
    └── 전체 흐름 조율
```

## 6. 최종 산출물

| 파일 | 용도 |
|------|------|
| `reports/evaluation_result.json` | 전체 평가 결과 (상세, 개발자용) |
| `reports/evaluation_result.csv` | 점수 요약표 (엑셀 열람용) |
| `reports/final_quality_report.md` | 최종 품질 보고서 (사람이 읽는 문서) |

## 7. 이 프로젝트로 얻는 것

| 능력 | 설명 |
|------|------|
| QA 자동화 설계 | 단순 챗봇 제작을 넘어 품질 관리 파이프라인 구성 경험 |
| Agent 역할 분리 | Service Agent(챗봇)와 Judge Agent(평가자)를 분리하는 구조 이해 |
| 데이터 기반 품질 관리 | "감"이 아닌 점수와 근거로 품질을 측정하는 방법 |
| 재현 가능한 결함 기록 | 같은 케이스를 반복 실행해도 동일한 방식으로 평가 가능 |
| 실무 확장 가능성 | 이 구조를 실제 운영 모니터링 시스템으로 확장 가능 |
