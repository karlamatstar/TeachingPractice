# 시연 시나리오 (약 12분)

> 사전 준비: OpenAI API 키에 크레딧이 남아있는지 미리 확인. 라이브 중 API 장애 대비용으로
> `_OUTPUT/quality/`(테스트케이스 리포트, 챗봇 로그 모두 포함)에 미리 한 번 돌려둔 결과를 백업해두면 안전합니다.

## 0. 오프닝 — 문제의식 (30초)

> "챗봇은 만드는 것보다 '계속 품질이 유지되는지 증명하는 것'이 더 어렵습니다. 이 프로젝트는
> 하나의 AI 에이전트를 기능 테스트 → AI 품질 평가 → 성능 테스트 → 실시간 모니터링까지
> 엔드투엔드로 검증하는 파이프라인입니다."

`_DOCS/README.md`의 파이프라인 다이어그램을 화면에 띄우고 시작.

## 1. 라이브 채팅 데모 (2분)

```bash
uvicorn app.main:app --reload
```

브라우저에서 `http://localhost:8000/docs` 열고 `POST /chat`에 3개를 순서대로 질문:

1. **정상 질문**: "이 교육과정은 총 몇 시간인가요?" → 정확한 답 확인
2. **오류 정정 유도(Edge)**: "총 훈련 시간이 300시간인가요?" → 320시간으로 정정하는지 확인
3. **적대 질문(Negative)**: 괴롭힘/프롬프트 해킹 시도 → 안전하게 거절하는지 확인

> 포인트: 답변 자체보다 "3가지 유형(Happy/Edge/Negative)을 다 갖춘 테스트 설계"를 강조.

## 2. 자동화된 테스트 (1분30초)

```bash
pytest -v
```

- `test_health.py` — 서비스 헬스체크
- `test_agent_api.py` — 방금 본 것과 같은 API 계약 검증 (자동화)
- `test_negative_cases.py` — 부정 케이스 3건 자동 검증

> 포인트: "방금 손으로 확인한 걸 코드가 매번 자동으로 재검증합니다."

## 3. AI Judge 배치 품질 회귀 (2분)

```bash
python -m quality.quality_pipeline
```

콘솔에 케이스별로 `PASS [정확성 5 | 근거성 5 | ... | 합계 23/25]` 흐르는 걸 보여주고,
생성된 `_DOCS/final_quality_report.md`를 열어 판정 배지 표/종합 요약 섹션을 스크롤.

> 포인트: 사람이 채점하지 않고 **LLM Judge가 5개 축(정확성/근거성/유용성/안전성/이해성)으로
> 자동 채점**한다는 것, 그리고 API 장애 시 FAIL이 아니라 **N/A로 구분**해 통과율이 왜곡되지
> 않는다는 설계.

## 4. Streamlit 품질 대시보드 (2분)

```bash
streamlit run dashboard/streamlit_app.py
```

- **배치 품질 현황**: PASS/REVIEW/FAIL/N/A KPI 카드, 케이스별 점수 막대그래프
- **유형별 비교**: Happy/Edge/Negative 레이더 차트
- **실시간 대화**: 1번 단계에서 방금 물어봤던 질문/답변이 그대로 리스트에 뜨는 것을 보여줌
  ("방금 API로 대화한 게 여기 실시간으로 로그로 남습니다")
- **종합 리포트**: 마크다운 리포트 렌더링

## 5. Docker Compose + 운영 모니터링 (3분) — 하이라이트

```bash
docker compose up --build -d
```

3개 컨테이너(app/prometheus/grafana)가 뜨는 걸 보여준 뒤:

1. Swagger(`/docs`)에서 `/chat`을 4~5번 연달아 호출 (또는 `k6 run performance/k6_test.js`로 부하 생성)
2. Grafana(`http://localhost:3000`) → "AI Agent Quality & Operations" 대시보드
   - 요청 처리량, 응답 지연 백분위(p50/p90/p99) 그래프가 움직이는 것
   - AI Judge 판정 추이·세부 항목별 평균 점수 그래프
3. Prometheus(`http://localhost:9090`)에서 raw 쿼리로 "이게 실제 숫자다"를 증명

> 포인트: "배치 테스트는 배포 전 게이트, 이 대시보드는 배포 후 운영 중 실시간 감시" —
> 역할이 분리되어 있다는 설계 의도를 명확히 짚기.

## 6. 장애 복원력 데모 (선택, 1분) — 차별점

`.env`의 키를 잠시 무효화하거나, 이미 겪었던 실제 429 quota 초과 상황을 그대로 재현:

- `/chat` 호출 → 3회 재시도 후 503
- Grafana의 "에이전트 재시도/N/A 발생" 그래프에 즉시 반영
- 배치 리포트에서는 FAIL이 아니라 **N/A**로 집계되는 것을 강조

> 포인트: "장애를 감추지 않고, 장애 자체를 관측 가능하게 설계했다"는 게 이 프로젝트의
> 가장 엔지니어링적인 부분.
