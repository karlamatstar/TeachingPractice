# K6 성능 테스트 파이프라인 설계 및 계획서

본 문서는 AI Agent 품질관리 운영플랫폼의 성능 테스트(Performance Testing) 아키텍처 및 구현 계획을 명세합니다.

## 1. 테스트 목적 및 과제
- **과제:** LLM(OpenAI) 기반의 비동기 백엔드(FastAPI)는 API 응답 지연과 비용, 그리고 Rate Limit(429 Too Many Requests)이라는 한계가 존재합니다.
- **목적:** 외부 API 종속성을 배제하고, 순수하게 개발된 **FastAPI 서버의 아키텍처 한계 성능**을 고립시켜서 측정하기 위함입니다.

## 2. 테스트 아키텍처 설계

### 2.1. 테스트 대상 엔드포인트 전략 (Mock API 도입)
과금 및 Rate Limit 방지를 위해 실제 `/chat` 엔드포인트 대신 가짜 API를 활용합니다.
- **실제 API (`/chat`):** 비용 발생, OpenAI 한계치에 종속됨. (필요 시 최소한의 Smoke Test에만 일부 사용)
- **가짜 API (`/chat_mock`):** 내부적으로 1~2초의 비동기 지연(Sleep)만 발생시키고 더미 응답을 반환. 서버 자체의 비동기 큐잉 및 동시 접속 처리량을 측정하기 위한 핵심 타겟. (`/docs`의 `[Performance Test]` 태그 하위에 노출)

### 2.2. 성능 모니터링 방식 및 대시보드 구성
- **수비수 시점 (서버 모니터링):** 기존에 구축된 "AI Agent 실시간 운영 모니터링" 대시보드를 활용해 서버 자원(CPU, 메모리)과 큐(Queue) 상태를 관측합니다.
- **공격수 시점 (K6 전용 대시보드 신규 생성):** Grafana에 `[K6 Performance Test]` 전용 탭(대시보드)을 새로 추가하여 다음 4가지 핵심 지표를 실시간 그래프로 보여줍니다.
  1. **VUs (활성 가상 유저):** 시간에 따라 투입되는 동시 접속자 수의 변화 (스트레스 테스트 시 우상향 그래프)
  2. **RPS (초당 요청 수):** 초당 서버를 때리고 있는 총 API 요청량
  3. **HTTP Latency (응답 지연 시간):** 평균, p90, p95 지연 시간을 통해 유저가 체감하는 대기 시간 시각화
  4. **Error Rate (요청 실패율):** 서버가 견디지 못하고 터진 5xx 에러 또는 타임아웃 비율

## 3. 진행할 4가지 K6 테스트 유형

K6 스크립트는 역할별로 명확히 분리하여 `performance/` 폴더 내에 개별 작성합니다. 모든 스크립트는 로컬(`127.0.0.1`)로 하드코딩하지 않고 환경 변수를 통해 타겟 IP를 동적으로 주입받아 팀 단위 원격 테스트를 지원합니다.

1. **Smoke Test (`smoke_test.js`)**
   - VUs: 1~2명
   - 목적: 시스템 인프라 정상 연결 및 `/health`, `/chat_mock` 경로의 즉각적인 200 OK 응답 여부 확인 (가벼운 건강 검진).
2. **Load Test (`load_test.js`)**
   - VUs: 10~50명 수준을 수 분간 유지
   - 목적: 예상되는 일상적인 트래픽 하에서 메모리 누수 없이 안정적인 처리가 가능한지 검증.
3. **Stress Test (`stress_test.js`)**
   - VUs: 단계적으로 한계점까지 끝없이 증가 (Step-up)
   - 목적: 서버가 더 이상 버티지 못하고 에러(503, Socket Hang up 등)가 발생하는 한계 지점 도출.
4. **Spike Test (`spike_test.js`)**
   - VUs: 순간적으로 0에서 급증 (예: 수강신청 등 피크 타임 시뮬레이션)
   - 목적: 트래픽 피크 상황에서의 시스템 복원력 및 큐잉 능력 검증.

## 4. 커스텀 GUI 런처 (performance_gui.py)
터미널 명령어에 익숙하지 않은 수업 참가자도 성능 시험을 쉽게 확인할 수 있도록 **Tkinter 기반의 K6 전용 GUI 클라이언트**를 구축합니다.

### 4.1. 핵심 UI/UX 설계
- **서버 IP 지정:** 팀원 공유용 접속 IP를 상단에 입력받아 모든 테스트의 타겟으로 설정. (기본값: LAN IP 자동 감지)
- **4-Tab 독립 제어:** Smoke, Load, Stress, Spike 각각의 탭에서 목적에 맞는 옵션(VUs, Duration)을 독립적으로 세팅.
- **상태 잠금(Locking) 안심 장치:** [테스트 시작] 시 중복 클릭 및 탭 이동을 비활성화하고, 명시적인 "진행 중" 상태 표시(인디케이터) 제공.
- **실시간 K6 콘솔 (통합 뷰):** GUI 하단에 커다란 텍스트 위젯을 배치하여 K6 백그라운드 프로세스의 `stdout` 결과를 실시간으로 스트리밍.

### 4.2. 결과 리포트 및 로그 관리 아키텍처 (JSON/CSV)
`_OUTPUT/quality` 폴더의 명명 규칙(`evaluation_result.json` 및 `YYYYMMDD_HHMMSS_evaluation_result.json`)을 완벽히 따릅니다.

- **최신 결과 (`_OUTPUT/performance/`):** 
  - 각 테스트별로 가장 마지막에 실행된 결과만 덮어쓰기로 유지합니다.
  - `smoke_result.json`, `load_result.json`, `stress_result.json`, `spike_result.json` (총 4개 유지)
- **누적 이력 (`_OUTPUT/performance/k6_log/`):**
  - 실행 시점의 타임스탬프(`YYYYMMDD_HHMMSS_`)를 파일명 **접두사(Prefix)**로 붙여 누적 저장합니다.
  - 예시: `20260707_123900_smoke_result.json`, `20260707_124530_load_result.json`

## 5. 결론
이 설계는 단순한 "부하 스크립트 작성"에서 확장해 **LLMOps 환경에서의 외부 API 자원 경합 해결(Mocking), 실시간 모니터링 통합(Grafana), GUI 기반 실행 흐름**을 함께 학습하도록 구성합니다.
