# 장애 시나리오 검증 테스트(Fault Lab) 운영 계획서

기존 운영 환경(정상 API + 로그 + Prometheus + Grafana + k6)에 영향을 주지 않으면서, 실습용 최소 장애 기능을 모의(Mock)로 구현하여 장애 대응 프로세스를 훈련하기 위한 계획서입니다. 
**모든 장애를 실제 프로그램 레벨로 복잡하게 구현하지 않고**, 전용 테스트 API(`/fault-lab`)를 통해 통제된 장애를 발생시킵니다.

## 1. 개요 및 목적
* **목표**: 응답 지연, 500 오류, 타임아웃 등 핵심 장애 3가지를 모의 발생시키고, 이를 탐지/보고/조치하는 전체 라이프사이클 실습
* **운영 프로세스**: 
  1. k6 및 자동화 테스트(Pytest)를 통한 장애 유발 및 탐지
  2. **결함 보고서(`_OUTPUT/quality/defects/chaos/defect_report.md`)** 작성 및 리포트화
  3. 원인 분석 및 조치 내용 기록 (의도적 장애 유발이므로 본 훈련에서 Jira 티켓 자동 생성은 생략)
  4. 재시험(Re-test) 수행

## 2. 실습용 최소 장애 API (`/fault-lab`) 설계
실제 비즈니스 로직 수정 없이, 파라미터(`scenario`)에 따라 장애를 모의하는 테스트용 API를 백엔드에 추가합니다.

* **구현 위치 및 Swagger 연동**: 현재 프로젝트의 FastAPI 메인 코드(`app/main.py`)에 엔드포인트를 주입합니다. 이를 통해 **Swagger UI(`/docs`)에 `/fault-lab` API가 자동으로 노출**되며, k6 같은 자동화 툴뿐만 아니라 QA 담당자가 직접 웹 화면에서 버튼을 눌러 수동으로 장애를 유발하고 테스트할 수도 있습니다.
* **엔드포인트**: `GET /fault-lab`
* **파라미터**: `scenario` (기본값: normal), `delay_seconds` (기본값: 0)

| `scenario` | 예상 동작 (HTTP 상태 코드) | 설명 |
|---|---|---|
| `normal` | 200 OK | 정상 응답 |
| `delay` | 200 OK | 지정된 `delay_seconds` 만큼 지연 후 응답 |
| `error500` | 500 Internal Server Error | 내부 서버 오류 강제 발생 |
| `timeout` | 504 Gateway Timeout | 의도적인 타임아웃 발생 (또는 지연 후 504) |
| `wrong` | 400 Bad Request | 잘못된 시나리오 파라미터 입력 시 예외 처리 |

## 3. 테스트 케이스 (TC)
| TC_ID | 테스트 항목 | 요청 주소 | 기대 결과 |
|---|---|---|---|
| FL-001 | 정상 응답 | `/fault-lab?scenario=normal` | HTTP 200, 정상 메시지 반환 |
| FL-002 | 응답 지연 1초 | `/fault-lab?scenario=delay&delay_seconds=1` | HTTP 200, 약 1초 후 응답 |
| FL-003 | 응답 지연 5초 | `/fault-lab?scenario=delay&delay_seconds=5` | HTTP 200, 약 5초 후 응답 |
| FL-004 | 500 오류 재현 | `/fault-lab?scenario=error500` | HTTP 500, 오류 메시지 반환 |
| FL-005 | 타임아웃 재현 | `/fault-lab?scenario=timeout&delay_seconds=3` | HTTP 504, 타임아웃 메시지 반환 |
| FL-006 | 잘못된 시나리오 | `/fault-lab?scenario=wrong` | HTTP 400, 잘못된 값 안내 |
| FL-007 | 자동 테스트 | GUI의 Pytest 탭 실행 또는 터미널 `pytest` 명령어 | 모든 테스트 PASS 판정 |
| FL-008 | 결함보고서 작성 | `_OUTPUT/quality/defects/chaos/defect_report.md` | 수집된 재현 결과와 QA 조치 의견이 정확히 양식에 맞춰 작성됨 |

**[테스트 케이스 작성 및 데이터화 관리]**
챗봇 품질 검증 로직과 동일한 설계 철학을 적용하여, 위 테스트 케이스들은 파이썬 코드에 하드코딩하지 않고 별도의 파일(예: `quality/chaos_test_cases.json`)을 만들어 데이터로 작성하고 관리해야 합니다. 이를 통해 기획자가 언제든 새로운 장애 시나리오나 임계치를 손쉽게 추가할 수 있습니다.

## 4. 장애 대응 및 리포트 운영 프로세스 (Workflow)

**[현업 QA 장애 대응 9단계 파이프라인 적용]**
본 기획은 실제 현장에서 요구하는 정석적인 대응 순서(`장애 발견 → 장애 재현 → 증상 확인 → 영향도 판단 → 로그/지표 확인 → 결함 등록 → 조치 요청 → 재시험 → 종료`)를 그대로 시스템(GUI+Jira+보고서)에 녹여내어 자동화하는 데 목적이 있습니다.

### 4.1. 통합 자동화 실행 (`test_launcher.py` '검증 테스트' 탭)
- **GUI 통합 운영 ('검증 테스트' 탭)**: 기존에 분리하려던 기능 테스트(Pytest) 탭과 장애 훈련(Chaos) 탭을 하나로 합친 **'검증 테스트' 탭**을 추가합니다.
- **순차적 파이프라인 트리거**: 탭 내의 '자동화 시작' 버튼을 누르면 다음 순서로 단 1번의 릴레이 실행이 진행됩니다.
  1. 장애 모의 훈련(`/fault-lab` 호출, FL-001 ~ 006)
  2. 전체 기능 및 품질 검증(Pytest 실행, FL-007)
  3. 테스트 결과 취합 및 결함 보고서 생성(FL-008)
- **결함 보고서 원격 열람 (Static 서빙)**: 모든 자동화 시퀀스가 끝나면 GUI에 **'결함 보고서 확인'** 버튼이 활성화됩니다. 챗봇 서버(FastAPI)가 `_OUTPUT/quality` 폴더를 정적 파일(Static Files)로 개방하므로, 버튼 클릭 시 즉각 웹 브라우저가 열려 서버 측 **마크다운(MD)** 보고서를 원격으로 열람할 수 있습니다.
- **실시간 터미널 뷰어**: 탭 하단의 터미널 창을 통해, 고의 장애 유발부터 파이테스트 통과 여부, 그리고 최종 보고서 생성까지 전체 파이프라인이 순차적으로 흘러가는 것을 한눈에 모니터링할 수 있습니다.

### 4.2. Jira 결함 등록 (비활성화)
- 기존에는 모니터링 중 발견된 장애를 Jira 프로젝트 보드에 `Bug` 유형으로 자동 등록하는 구조였으나, 고의로 장애를 유발하는 본 테스트의 성격상 티켓이 불필요하게 대량 생성되는 것을 방지하기 위해 **Jira 티켓 자동 생성 기능은 비활성화** 상태로 운영합니다.

### 4.3. 결함 보고서(`defect_report.md`) 작성 및 리포트화
장애 상황을 체계적으로 문서화하여 `_OUTPUT/quality/defects/chaos/defect_report.md`에 기록합니다.

**[파일 관리 전략]**
- **최신본 유지 (Overwrite)**: `_OUTPUT/quality/defects/chaos/defect_report.md` 파일은 항상 가장 최근에 수행된 테스트 결과로 덮어쓰기되어 깔끔하게 유지됩니다.
- **히스토리 아카이브 (Log)**: 테스트를 수행할 때마다 `_OUTPUT/quality/defects/chaos/log/` 하위 폴더에 타임스탬프가 포함된 파일(예: `defect_report_20260708_1305.md`)을 복사하여 과거 이력을 영구 보존합니다.

**[결함 보고서 작성 기준 및 항목]**
장애가 재현되면 `_OUTPUT/quality/defects/chaos/defect_report.md`에 현업 QA 가이드라인(8가지 필수 질문)에 맞추어 아래 내용을 기록합니다. 보고서 최상단에는 이번 훈련에서 **어떤 테스트들을 대상으로 진행했는지(테스트 범위)**를 반드시 명시합니다.

| 항목 | 시스템 자동 작성 내용 |
|---|---|
| **테스트 개요 및 대상** | 본 보고서에서 다루는 훈련 대상 시나리오(Delay, 500 오류 등) 목록 및 훈련 목적 |
| **결함 제목** | *(무슨 장애가 발생했는가?)* 예: 응답 지연 시 사용자 대기시간 증가 및 504 Timeout 발생 |
| **재현 절차** | *(어떻게 재현했는가?)* GUI 테스트 시작 클릭 ➔ `/fault-lab?scenario=delay&delay_seconds=3` 호출 |
| **기대 결과** | *(기대 결과는 무엇이었는가?)* 지연 없이 즉각적인 HTTP 200 정상 응답 |
| **실제 결과** | *(실제 결과는 무엇이었는가?)* 3초 지연 후 응답, 또는 500 에러 발생 (Grafana 로그 캡처 포함) |
| **영향도** | *(사용자에게 어떤 영향이 있는가?)* 페이지 로딩이 멈추어 사용자 이탈 발생, 결제 마비 위험 |
| **원인 추정** | *(원인은 무엇으로 추정되는가?)* 의도적인 `scenario` 파라미터 유발. (실제 시: DB 병목 등) |
| **조치 방안** | *(어떻게 조치해야 하는가?)* 타임아웃 2초 제한 설정, 사용자에게 안내 팝업 출력 등 |
| **재시험 결과** | *(조치 후 다시 테스트했는가?)* 조치 완료 후 재시험(Re-test) 수행 결과 PASS / FAIL 여부 기록 |

### 4.4. 최종 보고용 Word(.docx) 문서 변환 및 'QA 종합 의견' 추가
시스템이 자동 생성한 `_OUTPUT/quality/defects/chaos/defect_report.md` (3건의 결함 기록 포함)를 기반으로, 최종 제출용 워드(`_OUTPUT/quality/defects/chaos/final_defect_report.docx`) 문서를 생성합니다.
- **포맷 변환**: 파이썬(`python-docx`) 등을 활용하여 마크다운을 워드 포맷으로 자동 변환합니다.
- **의견 자동 생성**: 에러 발생 상황(상태 코드, 응답 시간, 에러 로그 등)을 바탕으로, **"전문 QA 엔지니어 관점에서의 원인 분석 및 시스템 조치 조언"**을 동적으로 생성합니다. (※ 실제로는 API가 작성하지만, 문서상에는 담당자가 직접 분석한 것처럼 자연스럽게 기재)

**[최종 Word 보고서 양식 (Template)]**
* **타이틀 및 요약**: 인프라 장애 모의 훈련(Chaos Test) 결과 보고서 / 총 발생 장애 건수
* **테스트 대상 및 범위**: 이번 모의 훈련에서 어떤 장애 시나리오(API 지연, 서버 다운 등)들을 타겟으로 테스트를 진행했는지 최상단에 명시.
* **장애 상세 내역 (표)**: 마크다운에 기록된 결함 내용(재현 경로, 실제 결과 등)을 워드의 표(Grid Table) 형태로 깔끔하게 변환.
* **💡 QA 엔지니어 검토 의견**: 워드 문서의 각 결함 항목 하단에, 담당자가 직접 세밀하게 작성한 듯한 '전문적인 테스트 의견'이 사람의 손길을 거친 뉘앙스(예: 파란색 텍스트 강조)로 추가됩니다.
* 이 양식을 통해 수업 시연이나 내부 검토 때 자동화 시스템이 보고서 생성까지 담당하는 흐름을 확인합니다.

### 4.5. 재시험 및 완료 (Closed)
- 조치 내용이 반영된 후, 동일한 k6/Pytest 시나리오를 다시 실행하여(Re-test) 에러가 해결되었는지 검증합니다.
- 테스트가 `PASS` 되면 결함 보고서를 최종 업데이트하고 Jira 티켓의 상태를 `Closed` (완료)로 변경하여 실습을 종료합니다.
