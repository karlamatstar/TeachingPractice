# 자동화 테스트(Pytest) 운영 및 구조 기획서

## 1. 개요
현재 프로젝트에 구축된 파이테스트(Pytest) 기반의 자동화 파이프라인 운영 계획입니다.
단순 부하 발생 도구인 k6에만 의존하지 않고, **"AI 챗봇의 비즈니스 로직(품질) 검증"**부터 **"인프라 장애 모의 훈련(Fault Lab)"**까지 모든 테스트를 Pytest라는 거대한 하나의 우산 아래 통합하여 한 번에 실행(One-Click Total Test)할 수 있도록 구조화하는 것이 핵심 목적입니다.

## 2. 테스트 아키텍처 (Data-Driven Test)
우리 시스템의 가장 큰 특징은 **데이터 주도 테스트(Data-Driven Test)** 구조를 채택했다는 점입니다.
* **로직과 데이터의 분리**: 파이썬 코드 안에 테스트 질문을 하드코딩하지 않고, 모든 테스트 케이스를 `quality/test_cases.json` 파일에서 동적으로 읽어와 실행합니다.
* **비개발자 친화적 유지보수**: 기획자나 QA 담당자가 파이썬 코드를 몰라도, JSON 파일에 "새로운 꼬투리 잡는 질문"과 "기대하는 정답 키워드"만 적어 넣으면 시스템이 알아서 수십, 수백 개의 테스트를 수행합니다.

## 3. 핵심 테스트 구성 (tests/ 폴더)
현재 프로젝트에 구성된 기존 5가지 품질 테스트에 **장애 테스트(Chaos)**를 추가하여, 총 6개의 핵심 테스트 스위트(Suite)로 통합 운영합니다.

| 파일명 | 테스트 유형 | 검증 목적 및 상세 내용 |
|---|---|---|
| **`test_health.py`** | 상태 검증 (Health Check) | FastAPI 서버가 죽지 않고 정상적으로 응답(200 OK)하는지 가장 먼저 확인하는 핑(Ping) 테스트입니다. |
| **`test_agent_api.py`** | API 연동 통합 테스트 | 실제 OpenAI API와 연결하여, 정상적인 사용자 질문("교육과정 몇 시간이야?")에 제대로 답을 내려주는지 검증합니다. |
| **`test_negative_cases.py`** | 적대적 방어 검증 (Negative) | 해킹 방법, 욕설 등 챗봇이 대답해서는 안 될 질문을 던졌을 때, 뚫리지 않고 정해진 멘트("도와드릴 수 없습니다")로 방어하는지 철저히 검사합니다. |
| **`test_quality_pipeline.py`** | 품질 평가 로직 검증 | 챗봇이 내뱉은 답변을 다시 채점 모델(`gpt-4o`)이 정확하게 채점(PASS/FAIL 판정)하고 있는지, 채점관 자체를 테스트합니다. |
| **`test_live_report.py`** | 파일 I/O 및 로깅 검증 | 평가 결과가 누락되지 않고 실시간으로 CSV나 JSON 리포트 파일에 잘 기록되고 있는지 검증합니다. |
| **`test_fault_lab.py` (통합 예정)** | 인프라 장애 모의 훈련 (Chaos) | GUI나 터미널에서 Pytest를 돌리면 한 번에 같이 실행되며, 고의로 장애(`/fault-lab`)를 유발한 뒤 Jira 결함 보고서가 정상 발행되는지 검증합니다. |

## 4. 이슈 사항 및 개선 워크플로우
테스트 중 발생할 수 있는 주요 실패(Fail) 사례와 대응 프로세스입니다.

* **발생 가능한 실패 유형 (TC-026 사례)**
  * 챗봇이 적대적 공격은 잘 방어했으나, 답변이 너무 유연해서 기획자가 JSON에 적어둔 **'기대 키워드'와 정확히 일치하지 않아 실패(AssertionError)** 처리되는 현상. (LLM 테스트의 고질적 한계)
* **대응 및 개선 (Feedback Loop)**
  1. 실패 로그를 분석하여 챗봇의 방어 프롬프트를 더 엄격하게 고정(Hard-prompting)하거나,
  2. 반대로 `test_cases.json`의 기대 키워드를 여러 개로 늘려 유연하게 채점하도록(Soft-matching) 테스트 코드를 개선합니다.
  3. 이 과정 자체를 시스템 고도화의 핵심 포트폴리오로 활용합니다.

## 5. GUI 연동 및 향후 확장 계획

### 5.1. GUI 통합 운영 (`test_launcher.py` '검증 테스트' 탭)
기존에 별도로 분리하려던 '장애 훈련 탭'과 '기능 검증 탭'을 하나로 합쳐 **'검증 테스트' 탭** 하나만 운영합니다.

- **원클릭 순차 실행 (Sequential Execution)**:
  탭 내의 'QA 자동화 시작' 버튼을 누르면 다음 순서대로 파이프라인이 한 번에(자동으로) 진행됩니다.
  1. **장애 모의 훈련 (Chaos Test)**: `/fault-lab`을 호출하여 500 에러, 타임아웃 등 인프라 장애를 고의로 유발 (FL-001 ~ FL-006)
  2. **Pytest (기능/통합 검증)**: 장애 발생 여부와 무관하게, 챗봇의 방어 로직과 품질 평가 등 순수 기능 테스트(Regression Test) 이어서 실행 (FL-007)
  3. **최종 결함 보고서 생성**: 장애 유발 결과와 Pytest 실행 결과를 모두 종합하여 Jira 티켓 및 Word 결함 보고서 생성 (FL-008)

- **결함 보고서 원격 열람 (버튼 활성화 및 Static 서빙)**: 릴레이 테스트가 모두 종료되면, GUI 상의 `[결함 보고서 확인]` 버튼이 활성화됩니다. FastAPI의 정적 파일(Static Files) 제공 기능을 활용하므로, 동료 PC에서 GUI를 실행했더라도 버튼 클릭 시 즉시 웹 브라우저를 통해 서버 쪽 리포트 URL(`http://서버IP:8000/reports/...`)로 원격 접속하여 보고서를 볼 수 있습니다.
- **터미널 모니터링**: 탭 하단 터미널 창을 통해 장애 발생 현황과 Pytest의 Pass/Fail 로그가 순차적으로 흘러가는 것을 실시간으로 모니터링합니다.

### 5.2. 지속적 통합(CI/CD) 연동
* 프롬프트나 백엔드 코드를 한 줄이라도 수정할 경우, CI/CD 파이프라인 단에서 위 Pytest 스크립트 6개가 자동으로 쫙 돌아가서 기존 기능이 망가지지 않았는지 샐 틈 없이 감시하도록 구성합니다.
