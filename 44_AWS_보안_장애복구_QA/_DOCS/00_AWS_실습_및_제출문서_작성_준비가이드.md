# AWS 웹 서버 구축·보안 점검·장애복구 실습 및 제출 문서 작성 가이드

> 문서 상태: **준비용**
>
> 현재는 AWS 콘솔 접속, 리소스 생성, 웹 서버 접속, 장애 발생, 스크린샷 촬영 및 제출 문서 작성을 수행하지 않는다.
> 실제 실습을 시작할 때 이 문서를 위에서 아래 순서대로 사용한다.
>
> 최종 확인일: 2026-07-24

---

## 1. 이 문서의 목적

이 문서는 다음 네 개의 제출 파일을 실제 실습 결과에 맞게 작성하기 위한 준비·실행·증빙·정리 절차를 정의한다.

1. `01_웹서버_정상화면.png`
2. `02_보안설정_점검표.xlsx`
3. `03_장애복구_결과표.xlsx`
4. `04_최종실습보고서.docx`

중요한 원칙은 다음과 같다.

- AWS에서 실제로 확인한 내용만 작성한다.
- 실행하지 않은 항목을 `적합`, `PASS`, `완료`로 작성하지 않는다.
- 화면 캡처와 명령 출력은 판정을 뒷받침하는 증빙으로 사용한다.
- **`02_보안설정_점검표.xlsx`의 10개 항목마다 증빙 스크린샷이 필요하다.**
- **`03_장애복구_결과표.xlsx`의 8개 단계마다 증빙 스크린샷이 필요하다.**
- 각 스크린샷의 파일명을 해당 엑셀 행의 `증빙 파일명` 또는 `증빙/비고`에 기록한다.
- 교육장 지침에서 허용한다고 확인되지 않는 한 같은 스크린샷을 여러 항목에 재사용하지 않는다.
- 비밀번호, 액세스 키, 비밀 액세스 키, MFA 인증번호, 개인 키는 절대 캡처하거나 문서에 입력하지 않는다.
- 비용이 발생할 수 있는 리소스는 실습 직전에 만들고, 제출용 증빙이 확보된 후 정리한다.
- 계정·교육장 지침이 이 문서와 다르면 교육장 지침을 우선한다.

## 2. 폴더 운영 원칙

현재 작업 폴더:

```text
D:\_aws_reports
├─ 00_AWS_실습_및_제출문서_작성_준비가이드.md
├─ 원본
│  ├─ KakaoTalk_20260723_103917922.png
│  ├─ 02_보안설정_점검표.xlsx
│  ├─ 03_장애복구_결과표.xlsx
│  └─ 04_최종실습보고서.docx
└─ 작업결과
   ├─ 01_웹서버_정상화면.png
   ├─ 02_보안설정_점검표.xlsx
   ├─ 03_장애복구_결과표.xlsx
   ├─ 04_최종실습보고서.docx
   └─ 증빙스크린샷
      ├─ 02_보안설정
      └─ 03_장애복구
```

운영 규칙:

- `원본` 폴더는 읽기 전용 보관본으로 취급한다.
- 모든 입력·수정·이미지 합성은 `작업결과` 폴더의 복사본에만 수행한다.
- 작성 중 문제가 생기면 `원본`에서 다시 복사하여 복구한다.
- 최종 제출 전에는 `작업결과` 폴더에 제출 대상 4개만 남기는 것을 원칙으로 한다.
- 임시 이미지, 메모, 콘솔 출력 파일이 필요하면 별도의 `증빙_임시` 폴더를 만들어 사용하고 최종 제출 범위를 확인한다.
- `02`와 `03`의 항목별 필수 스크린샷은 임시 파일이 아니므로 `작업결과\증빙스크린샷` 아래에 항목별로 보관한다.
- 최종 제출 시 증빙 폴더 자체를 함께 제출할지, 엑셀에 이미지를 삽입할지, 별도 ZIP으로 제출할지는 교육장 지침을 확인한다.

- 비용 발생 가능성 확인
- 최종 제출 파일 4개와 양식 구조 확인

- MFA 등록·사용 상태 확인

## 6. AWS IAM 준비 및 보안 기준

### 6.1 로그인 계정

양식의 안전 기준은 “루트 계정이 아닌 IAM 사용자 사용”이다.

준비 기준:

- 일상 실습에 루트 사용자를 사용하지 않는다.
- 교육장에서 제공한 IAM 사용자 또는 허용된 역할을 사용한다.
- 사용자명은 보고서에 입력할 수 있지만 비밀번호는 기록하지 않는다.
- 액세스 키가 필요하지 않은 실습이면 새 액세스 키를 만들지 않는다.
- CLI 작업이 필요해도 가능하면 임시 자격 증명 또는 교육장 제공 방법을 따른다.

### 6.2 MFA

확인할 내용:

- IAM 사용자 또는 지정된 로그인 계정에 MFA가 연결되어 있는지 확인
- 로그인 시 MFA 인증을 실제로 사용하는지 확인
- MFA 기기 이름 또는 등록 여부만 증빙하고 인증번호는 캡처하지 않음

증빙에 포함할 수 있는 정보:

- 사용자명
- MFA 기기 할당 상태
- MFA 활성 상태

증빙에서 제외할 정보:

- 현재 MFA 6자리 코드
- QR 코드
- 복구 코드
- 비밀번호
- 액세스 키 ID
- 비밀 액세스 키

## 7. EC2 생성 예정 설정

아래 값은 실습 양식과 현재 준비 기준을 맞춘 권장안이다. 실제 생성 전 교육장 지침과 계정 비용 조건을 다시 확인한다.

### 7.1 기본 설정

| 항목 | 예정 설정 | 확인 이유 |
|---|---|---|
| 리전 | 서울 `ap-northeast-2` | 보고서 양식의 실습 환경 |
| 인스턴스명 | 사전에 정한 고유 이름 | 문서 간 식별값 통일 |
| AMI | Amazon Linux 2023 | 보고서 양식 및 `dnf`, `systemctl` 명령과 일치 |
| 아키텍처 | 교육장 지침 우선, 일반적으로 x86_64 | 인스턴스 유형과 호환 필요 |
| 인스턴스 유형 | 교육장 지침 우선 | Free Tier와 비용 조건은 계정별로 다를 수 있음 |
| 구매 옵션 | 일반 실습은 On-Demand 예정 | 장애복구 실습 중 임의 종료 위험 방지 |
| 키 페어 | 새 키 또는 지정된 기존 키 | SSH 접속용 |
| VPC | 교육장 지정 VPC 또는 기본 VPC | 퍼블릭 접속 가능 여부 확인 |
| 서브넷 | 퍼블릭 IPv4 할당 가능한 서브넷 | 브라우저 접속 필요 |
| 퍼블릭 IP | 활성화 예정 | 정상 화면의 주소창 증빙 필요 |
| 메타데이터 | 가능하면 IMDSv2 필수 | 인스턴스 메타데이터 보안 강화 |

주의:

- `t3.micro` 등의 소형 유형도 계정 생성일·리전·Free Tier 상태에 따라 비용이 발생할 수 있다.
- 퍼블릭 IPv4 주소도 비용 대상이 될 수 있으므로 AWS Billing과 현재 가격을 확인한다.
- 실습을 시작할 준비가 끝난 후 인스턴스를 생성하여 불필요한 실행 시간을 줄인다.

### 7.2 EBS 루트 볼륨 예정 설정

| 항목 | 예정 설정 |
|---|---|
| 볼륨 유형 | `gp3` |
| 용량 | 교육장 지침 우선, 별도 지침이 없으면 8 GiB 검토 |
| IOPS | 기본 3,000 범위 검토 |
| 처리량 | 기본 125 MiB/s 범위 검토 |
| 암호화 | 계정 기본값 또는 교육장 지침 확인 |
| 종료 시 삭제 | 실습용이라면 활성화 예정 |

생성 직전 확인:

- [ ] 추가 데이터 볼륨이 불필요하게 생성되지 않는가
- [ ] 루트 볼륨의 `Delete on termination`이 의도대로 설정되었는가
- [ ] 스냅샷이 자동으로 생성되는 정책이 있는가
- [ ] 종료 후 남는 볼륨이 없는지 확인할 계획이 있는가

## 8. EC2 보안 그룹 예정 설정

### 8.1 인바운드 규칙

| 용도 | 프로토콜 | 포트 | 소스 | 판정 기준 |
|---|---:|---:|---|---|
| SSH 관리 | TCP | 22 | 현재 작업 PC의 공인 IPv4 `/32` | `내 IP/32만 허용` |
| 웹 접속 | TCP | 80 | 실습 요구에 따라 `0.0.0.0/0` | 외부 브라우저 접속 가능 |

예시:

```text
SSH   TCP 22   203.0.113.10/32
HTTP  TCP 80   0.0.0.0/0
```

위 IP는 예시이므로 실제로 사용하지 않는다.

보안 기준:

- SSH 22 포트에 `0.0.0.0/0`을 사용하지 않는다.
- SSH 소스는 AWS 콘솔의 `My IP` 또는 확인된 공인 IP `/32`로 제한한다.
- HTTP 80은 제출용 외부 접속이 필요할 때만 허용한다.
- HTTPS 443, RDP 3389, DB 포트 등 사용하지 않는 포트는 추가하지 않는다.
- IPv6를 사용하지 않으면 `::/0` 규칙을 불필요하게 추가하지 않는다.
- 교육장 네트워크의 공인 IP가 실습 도중 변경되면 SSH 규칙을 새 IP `/32`로 갱신한다.

### 8.2 아웃바운드 규칙

간단한 교육용 구축에서는 패키지 설치를 위해 기본 아웃바운드 허용 규칙을 사용할 수 있다. 교육장 정책이 있으면 해당 정책을 우선한다.

### 8.3 보안 그룹 증빙

캡처 시 다음 내용이 한 화면에서 확인되도록 한다.

- 보안 그룹 이름
- 인바운드 규칙
- TCP 22
- SSH 소스 IP `/32`
- TCP 80
- 불필요한 인바운드 포트가 없다는 점

## 10. S3 버킷 예정 설정

보고서에 S3 버킷명과 보안 점검 항목이 있으므로 실제 실습 지침에서 버킷 생성이 요구되는지 먼저 확인한다.

### 10.1 버킷 기본 설정

| 항목 | 예정 설정 |
|---|---|
| 버킷명 | 사전에 정한 전역 고유 이름 |
| 리전 | 서울 `ap-northeast-2` |
| 객체 소유권 | ACL 비활성화 / Bucket owner enforced 검토 |
| 퍼블릭 액세스 차단 | 4개 항목 모두 활성화 |
| 버킷 버전 관리 | 교육장 요구 시 활성화 |
| 기본 암호화 | SSE-S3 확인 |

S3의 새 객체는 기본적으로 서버 측 암호화가 적용되지만, 제출 점검표에는 암호화 확인이 있으므로 콘솔에서 실제 상태를 직접 확인하고 증빙한다.

### 10.2 퍼블릭 액세스 차단 확인 항목

다음 네 항목이 모두 활성화되어야 한다.

- [ ] 새 ACL을 통해 부여되는 퍼블릭 액세스 차단
- [ ] 임의의 ACL을 통해 부여되는 퍼블릭 액세스 차단
- [ ] 새 퍼블릭 버킷 정책 또는 액세스 포인트 정책 차단
- [ ] 퍼블릭 및 교차 계정 액세스를 허용하는 정책 제한

### 10.3 S3 증빙 주의사항

- 버킷을 공개 웹 호스팅 용도로 전환하지 않는다.
- `Principal: "*"` 정책을 불필요하게 추가하지 않는다.
- 액세스 키나 비밀 액세스 키를 객체나 파일명에 넣지 않는다.
- 제출 자료를 버킷에 올리는 경우 민감정보 검사 후 업로드한다.
- 실습 종료 시 버킷 유지 또는 삭제 여부는 교육장 지침을 따른다.

## 13. `03_장애복구_결과표.xlsx` 실행 및 작성 기준

작업 파일:

```text
작업결과\03_장애복구_결과표.xlsx
```

상단에 입력할 값:

- 교육생 이름
- 실습일
- EC2 인스턴스명
- 장애 유형: `웹 서버 중지`

판정 값:

- `PASS`: 실제 결과가 예상 결과와 일치
- `FAIL`: 실행했지만 예상 결과와 불일치
- `미실행`: 아직 실행하지 않음

> **필수 증빙 규칙**
>
> 8개 장애복구 단계마다 스크린샷 1개 이상을 준비한다.
> 명령 실행 단계는 명령어와 실행 후 프롬프트 또는 결과가 함께 보이게 캡처한다.
> 브라우저 확인 단계는 주소창과 정상·실패 상태가 함께 보이게 캡처한다.
> 스크린샷을 촬영한 직후 파일명을 해당 행의 `증빙/비고`에 기록한다.

증빙 수량 원칙:

- 기본 증빙은 **8개 단계 × 단계별 1장 = 총 8장**이다.
- 명령 입력 화면과 실행 결과 화면을 각각 찍어 단계마다 2장을 만들 필요는 없다.
- 명령 단계는 Enter를 누르기 전 입력 화면이 아니라, **명령 실행 후 명령어와 종료 결과가 한 화면에 함께 보이는 상태**를 촬영한다.
- `stop`과 `start`는 성공해도 별도 출력이 없을 수 있으므로 종료 코드 `0`을 함께 출력한다.
- 중지·복구 상태는 각각 다음 단계에서 `inactive`, `active` 결과를 별도 촬영한다.
- 사용자 지침에 따라 각 행에 독립된 스크린샷을 연결하며, 동일 파일을 여러 행에 재사용하지 않는다.

### 13.1 장애복구 실습 전 조건

- [ ] EC2 상태 검사 2/2 통과
- [ ] SSH 접속 가능
- [ ] `httpd`가 `active (running)`
- [ ] 브라우저에서 정상 페이지 접속 가능
- [ ] 퍼블릭 IP 기록 완료
- [ ] 시작 시각을 기록할 준비 완료
- [ ] 중지 명령을 실행해도 SSH는 유지된다는 점 이해

### 13.2 명령 실행용 브라우저 터미널 준비

`AWS CloudShell`은 대상 EC2와 별개의 환경이다. CloudShell에서 `sudo systemctl stop httpd`를 바로 실행하면 대상 EC2의 Apache가 중지되는 것이 아니므로 장애복구 명령 입력용으로 사용하지 않는다.

브라우저 안에서 대상 EC2에 직접 명령을 실행하려면 다음 방식 중 하나를 사용한다.

1. **권장: AWS Systems Manager Session Manager**
   - EC2에 `AmazonSSMManagedInstanceCore` 권한을 가진 IAM 역할 연결
   - SSM Agent 실행 상태 확인
   - 아웃바운드 HTTPS 443 통신 가능
   - EC2 콘솔에서 `인스턴스 선택 → 연결 → Session Manager → 연결`
2. **대안: EC2 Instance Connect**
   - 대상 인스턴스에 EC2 Instance Connect가 설치되어 있어야 함
   - IAM 연결 권한과 네트워크 조건 필요
   - AWS 콘솔 연결 방식은 EC2 Instance Connect 서비스용 SSH 소스 규칙이 필요할 수 있음

과제의 `SSH 22 = 내 IP/32` 조건과 충돌하지 않도록 기본적으로 Session Manager 사용 가능 여부를 먼저 확인한다.

연결이 완료되면 브라우저 터미널 안에서 다음 명령으로 대상이 맞는지 확인한다.

```bash
hostname
date '+%F %T %Z'
sudo systemctl status httpd --no-pager -l
```

인스턴스 식별 정보와 `httpd` 상태가 예상과 일치할 때만 장애복구를 시작한다.

### 13.3 단계별 실행 절차

#### 단계 1: 장애 전 정상 확인

브라우저:

```text
http://<EC2 퍼블릭 IPv4>
```

기록:

- 실제 결과: 웹페이지 정상 표시
- 시작 시각
- 종료 시각
- 판정: 실제 확인 후 `PASS`
- 필수 스크린샷: `03_01_장애전정상확인.png`

#### 단계 2: 웹 서버 중지

```bash
date '+%F %T %Z'
sudo systemctl stop httpd
echo "stop exit=$?"
```

기록:

- 실제 결과: `stop exit=0` 확인
- 판정: 실제 실행 후 결정
- 필수 스크린샷: `03_02_웹서버중지.png`

촬영 기준:

- 명령어를 입력만 한 상태에서는 촬영하지 않는다.
- 세 명령을 모두 실행한 후 `sudo systemctl stop httpd`와 `stop exit=0`이 한 화면에 함께 보일 때 촬영한다.
- 이 화면 1장으로 단계 2의 명령 실행 증빙을 구성한다.
- `inactive` 상태는 단계 3에서 별도로 확인하고 촬영한다.

#### 단계 3: 중지 상태 확인

```bash
date '+%F %T %Z'
sudo systemctl is-active httpd
sudo systemctl status httpd --no-pager -l
```

기대 결과:

```text
inactive
```

`systemctl status`가 비활성 서비스에 대해 0이 아닌 종료 코드를 반환할 수 있으므로, 화면의 `inactive` 상태를 기준으로 확인한다.

- 필수 스크린샷: `03_03_중지상태확인.png`
- 촬영 기준: 명령어와 `inactive` 결과가 한 화면에 함께 보여야 한다.

#### 단계 4: 장애 증상 확인

브라우저를 새로 고침한다.

기대 결과:

- 웹페이지 접속 실패
- 연결 거부 또는 시간 초과

기록:

- 실제 브라우저 메시지
- 확인 시각
- 판정
- 필수 스크린샷: `03_04_장애증상확인.png`

#### 단계 5: 장애 원인 기록

원인 기록 예시:

```text
Apache httpd 서비스가 중지되어 TCP 80 요청을 처리할 웹 서버 프로세스가 실행되지 않았다.
```

실제 확인 내용이 다르면 실제 원인을 기록한다.

- 필수 스크린샷: `03_05_장애원인확인.png`
- 원인 확인에 사용한 `systemctl status`, `is-active`, 브라우저 실패 화면 등의 근거가 보이게 한다.

원인 확인용 예정 명령:

```bash
date '+%F %T %Z'
sudo systemctl is-active httpd
sudo ss -lntp 'sport = :80'
```

촬영 기준:

- `inactive` 상태와 TCP 80 포트의 LISTEN 프로세스가 없다는 점이 확인되어야 한다.
- 단계 3과 같은 상태를 확인하더라도 단계 5용 명령을 다시 실행하고 별도 스크린샷으로 저장한다.

#### 단계 6: 웹 서버 복구

```bash
date '+%F %T %Z'
sudo systemctl start httpd
echo "start exit=$?"
```

- 필수 스크린샷: `03_06_웹서버복구.png`

촬영 기준:

- 세 명령을 모두 실행한 후 `sudo systemctl start httpd`와 `start exit=0`이 한 화면에 함께 보일 때 촬영한다.
- 이 화면 1장으로 단계 6의 명령 실행 증빙을 구성한다.
- `active` 상태는 단계 7에서 별도로 확인하고 촬영한다.

#### 단계 7: 복구 상태 확인

```bash
date '+%F %T %Z'
sudo systemctl is-active httpd
sudo systemctl status httpd --no-pager -l

```

기대 결과:

```text
active
```

- 필수 스크린샷: `03_07_복구상태확인.png`
- 촬영 기준: 명령어, `active` 상태 및 로컬 HTTP 응답이 한 화면에서 확인되어야 한다.

#### 단계 8: 최종 접속 확인

브라우저에서 다시 접속하거나 새로 고침한다.

기대 결과:

- 웹페이지 정상 표시
- 필수 스크린샷: `03_08_최종접속확인.png`

- 모두 `PASS`이면 `PASS`
